# Lessons: General / 汎用的な実装ミス

特定ドメインに該当しない汎用的な手戻り・ミス・アンチパターンの記録。
プロジェクトが成熟したら、ここから `shift-algorithm.md` / `css.md` / `security.md` 等の専門カテゴリへ切り出すこと。

## 📌 Master Rules

1. **「動かない」と言われたら推測で答えない** — エラーメッセージ・ログ・実行コマンド・該当ファイルを必ず先に確認する（→ #L-G002）。
2. **インラインスタイルは装飾目的では絶対に書かない** — ユーティリティクラスかコンポーネントクラスで解決（→ #L-G001）。
3. **ボイラープレート的なエラーハンドリングを盛らない** — フレームワーク保証されたパスや内部呼び出しに防御的 try-catch を重ねない。境界（ユーザー入力・外部API）でのみ検証する（→ #L-G003）。

## 教訓ログ

### 2026-01-01 [CSS][Frontend] L-G001: インラインスタイル `style="..."` で装飾を直書き
→ サマリ昇格 (2026-01-01: 装飾系インラインスタイル禁止)

- **❌ Anti-pattern (どんなミスをしたか):**
  HTML/JSに `style="margin-bottom:24px; color:#3B82F6;"` のような装飾系インラインスタイルを直書きしてしまった。デザインシステムの変数を経由しないため、後続のテーマ調整・余白スケール統一でハードコード値が散在し、全置換が必要になった。

- **✅ Solution / Rule (どうすれば防げるか):**
  - 装飾（色・余白・フォントサイズ・ボーダー等）は **必ず** ユーティリティクラスかコンポーネントクラスで表現する。
  - 動的値（JS制御・計算結果・ユーザー設定等）のみ `style` 属性使用を許容する。
  - 既存にユーティリティが無い場合は、CSSファイルに新規ユーティリティとして追加してから使う。

### 2026-01-01 [Debug][Process] L-G002: 「動かない」報告に推測で返答
- **❌ Anti-pattern (どんなミスをしたか):**
  ユーザーから「ボタンが動かない」と報告を受けた際、エラーメッセージや実行コマンドを確認せず「たぶんイベントリスナーの登録順序では」と推測で回答した。実際の原因は別レイヤーにあり、無駄な往復が発生した。

- **✅ Solution / Rule (どうすれば防げるか):**
  - バグ報告を受けたら、まず以下の3点をユーザーに確認する／自分で取得する：
    1. **エラーメッセージ**（コンソール / ネットワーク / サーバーログ）
    2. **実行コマンド・操作手順**（再現方法）
    3. **該当ファイルの最新状態**（直近の変更差分）
  - これらが揃うまで「原因の推測」で時間を使わない。

### 2026-01-01 [Refactor][YAGNI] L-G003: 不要なエラーハンドリング・抽象化の追加
- **❌ Anti-pattern (どんなミスをしたか):**
  バグ修正タスクで該当行を直すついでに、周辺コードに「念のため」の try-catch・null チェック・将来用の interface を追加してしまった。レビューで「タスク範囲外」と差し戻され、再コミットになった。

- **✅ Solution / Rule (どうすれば防げるか):**
  - 修正は **タスクが要求する最小範囲** に留める。
  - エラーハンドリング・バリデーションは **システム境界（ユーザー入力・外部API）** だけで行う。
  - 「将来こうなるかも」で抽象化を先取りしない（YAGNI）。3度目に同じパターンが現れたら抽象化する。
