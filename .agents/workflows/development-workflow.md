# 開発・データ同期 ワークフロー規定

このドキュメントは、本番環境のデータを保護し、安全かつ迅速に機能開発を進めるための **絶対ルール** を定義する。

---

## 📌 絶対ルール（最優先）

1. **コードは「上り」、データは「下り」**: ローカル → 本番 へ流すのは **コード（プログラム）だけ**。データ（DB・画像・設定）の **ローカル → 本番アップロードは絶対禁止**。
2. **破壊的Git操作の前にバックアップブランチ**: `git reset --hard` / `git push --force` 等の前は必ずバックアップブランチ作成をユーザーに提案・合意してから実行。
3. **複数環境作業時は `git fetch` → `git status` を必ず先に**: ローカル変更とリモートの乖離を確認してから作業を始める。

---

## 1. 原則：コードとデータの分離（一方通行）

### 【コード（プログラム）は「上り」】

ローカル環境（PC）で変更を行い、Git コミット → リポジトリ → CI/CD 経由で本番環境へ自動配備する。

> **理由:** 本番サーバー上で直接コードを書き換えることは、デグレ（先祖返り）や事故のもとになるため厳禁（緊急パッチを除く）。

### 【データ（DB・画像・設定等）は「下り」】

本番環境に蓄積された顧客データ・管理者設定を、ローカルへ定期的にダウンロードして同期する。

> **理由:** ローカルで作ったダミーデータを本番へアップロードすると、本物の顧客データが上書き・消滅する大事故に繋がる。データの「上り（ローカル → 本番）」は **絶対禁止**。

---

## 2. 開発開始時のデータ同期手順（Pull Data）

新しい大きな機能開発に着手する際、またはローカルと本番のデータ乖離が大きくなった際は、本番データをローカルへ下ろして同期する（または同等のダミーシードを流し込む）。

### 一般的なフロー
1. **本番環境でのエクスポート**:
   - DB ダンプツール（`mysqldump`, `pg_dump`, All-in-One WP Migration 等）でデータベース・メディアをエクスポート
   - バックアップファイルをローカルへダウンロード
2. **ローカル環境へのインポート**:
   - ローカルの開発環境 DB に取り込み、上書き復元
3. **環境変数の再確認**:
   - 本番のデータに引っ張られて外部 API の接続先が「本番用」にならないよう、`.env` 等を確認
   - `[ENV_MODE]` / `STRIPE_MODE` 等が **テストモード** であることを担保

### よくある事故
- 本番データを取り込んだ直後、外部 API キーが本番のままだったため、テストデータで本番にメール送信してしまった
- 本番データのインポート後、ローカルで作った検証用ユーザーが消失した（事前にエクスポートしておく）

---

## 3. CI/CD によるデプロイメント（Push Code）

1. ローカルでの動作確認（lint, test 等）が完了したら、変更ファイルを `git commit`
2. ブランチに `git push`
3. CI/CD パイプライン（GitHub Actions 等）が作動し、本番環境へ自動デプロイ

詳細は `.agents/workflows/deploy.md` 参照。

## 4. 複数PC・複数環境作業時のGitルール（必読）

別環境で作業を開始する前、必ず以下を実行：

```bash
git fetch origin
git status
```

`git status` の結果に応じて対応を変える：

| 表示 | 対応 |
|---|---|
| `Your branch is up to date with 'origin/<branch>'` | そのまま作業開始してOK |
| `Your branch is behind 'origin/<branch>' by N commits` | `git pull` で取り込んでから作業 |
| `Your branch and 'origin/<branch>' have diverged` | 状況確認の上、必要なら **バックアップブランチ作成 → `git reset --hard origin/<branch>`** で強制同期（ローカル未push変更は消失するため要合意） |

> ⚠️ `reset --hard` / `git push --force` 等の破壊的操作は、**実行前に必ずユーザーへバックアップブランチ作成を提案し、合意を得てから** 実行する。

### バックアップブランチの作り方
```bash
git branch backup/$(date +%Y%m%d-%H%M%S)
# または明示的に
git branch backup/before-reset-2026-05-05
```

## 5. ブランチ戦略（推奨）

| ブランチ | 用途 |
|---|---|
| `main` | 本番デプロイ対象。直接 push せず PR 経由で merge |
| `develop` | 開発統合ブランチ（採用する場合） |
| `feature/*` | 機能開発・改修のフィーチャーブランチ |
| `fix/*` | バグ修正用 |
| `hotfix/*` | 本番緊急修正用（main から切る） |
| `backup/*` | 破壊的操作前のバックアップ |

> プロジェクトに応じて GitHub Flow（main + feature のみ）/ Git Flow / トランクベース等を選択。

## 6. コミット規約

[Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) に準拠する。

| プレフィックス | 用途 |
|---|---|
| `feat:` | 新機能 |
| `fix:` | バグ修正 |
| `refactor:` | 動作を変えないコード整理 |
| `style:` | フォーマット・スペース等（コード意味は変えない） |
| `docs:` | ドキュメントのみ |
| `test:` | テスト追加・修正 |
| `chore:` | ビルド・依存関係等の雑務 |
| `perf:` | パフォーマンス改善 |

```bash
git commit -m "feat(booking): 予約モーダルの担当スタッフ選択機能を追加"
git commit -m "fix(auth): OTP検証後のセッション再生成漏れを修正"
```

---

## 7. PR 作成時のチェックリスト

- [ ] lint / test / type-check がローカルで通っているか
- [ ] コミットメッセージが Conventional Commits 準拠か
- [ ] PR タイトル・説明に「何を」「なぜ」が書かれているか
- [ ] 影響範囲（フロント／バック／DB／設定）が明示されているか
- [ ] 破壊的変更（API 変更・DB マイグレーション）の場合、ロールバック手順を記載したか
- [ ] スクリーンショット添付（UI 変更の場合）
